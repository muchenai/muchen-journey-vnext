# 本地 AI 自查

本地测试使用 `APP_ENV=local/test`。生产启用方案见 `deploy/ai-self-check/README.md`，要求独立文档应用和密钥文件挂载。使用现有学员端的“开始 AI 自查”和“历史 AI 自查记录”，不改变审核、提交、解锁或毕业码逻辑。

## 本地配置

在被 Git 忽略的 `.env` 中配置 `AI_SELF_CHECK_ENABLED=true`、`AI_BASE_URL`、`AI_MODEL`、`AI_API_KEY`。密钥只传入 API 容器，不进入网页镜像、浏览器或版本库。

文档读取、评论可单独配置 `AI_FEISHU_APP_ID` 和 `AI_FEISHU_APP_SECRET`（必须成对设置），不会改变飞书登录使用的 `FEISHU_APP_ID` 和 `FEISHU_APP_SECRET`，也不改变已有用户身份。未配置独立凭证时沿用登录应用的整套凭证。密钥仅保存在被忽略的本地 `.env` 和 API 容器中。文档应用身份需要：

- `docx:document:readonly`：读取文档正文及标题块。
- `wiki:node:read`：将知识库链接解析为文档。
- `slides:presentation:read`：读取 Day 1 公司介绍幻灯片中的文字和讲者备注。
- `docs:document.comment:create`：在标题块添加一条汇总评论。
- 重新自查还需要读取评论和更新原回复的权限（`docs:document.comment:read`、`docs:document.comment:update`，或飞书列出的可替代权限）。使用原评论的应用身份。

权限需发布生效，文档本身还必须允许应用访问。CLI 的个人授权不等于项目应用拥有权限。

## 规则及边界

- 宝藏一至四：根据用户指定的答案文档及现有任务题目进行对照，忽略资料中的分值说明。
- Day 1：正文 200–2000 个非空白字符，不计标题、评论；与公司和两份材料相关；不辱骂公司，合理批评不视为辱骂。
- 测评一至三：使用用户确认的 rubric，给出证据和修改建议，不计分。
- 仅支持可完整读取的文字文档，包括普通文档表格。图片、嵌入电子表格、附件等不会假装已读懂，会明确提示先整理文字。不会自动打开学员正文里的额外链接。
- Day 1 材料二为飞书幻灯片，读取每页文字及讲者备注，并明确向模型标注未识别图片的边界；不以无法核对图片内容为由判错。
- 参考资料读取失败、文档读取不全、模型返回不完整或带评分时，不发送评论，不报告成功。
- 正文最多 60000 字，总输入最多 100000 字；超限明确失败，不截断后冒充完整评价。
- 模型调用只发送当前任务必需的正文与参考资料，不发送账号手机号或凭据。参考资料及学员答案中的指令均作为不可信数据处理。

## 持久化和重试

`ai_self_checks` 保存当前任务和文档的处理状态、规则版本、模型、文档版本、输入摘要、评价和评论 ID。每个组织内同一文档只允许一条记录。知识库链接先解析为真实 docx token，防止换链接重复评论。历史记录按学员和任务隔离，沿用毕业码迁移后的历史身份解析。

状态为 `RUNNING → SENDING → COMPLETED`。读取或模型失败进入 `FAILED`，可重试。首次发布需确认评论 ID；后续更新需确认原回复更新成功。发送后网络超时进入 `UNCERTAIN`，不会自动再次发布。进程在发送阶段退出时保留 `SENDING`，由管理员核对，禁止盲目重发。十分钟前卡住的读取/模型阶段允许用新的 attempt ID 接管，旧处理不能再发表评论。

文档内容（标题、正文及正文计数）未变化时返回已有评价，不重复调用模型。内容变化后，将上次成功评价及时间、模型、文档版本追加保存到 `archived_results`，重新自查并以 PUT 更新原评论的根回复。仅版本号变化但内容未变不重新生成。0037 迁移前的记录首次按原文档版本判断，随后补全内容摘要。原评论不见或无法确认时失败，不新增替代评论；模型失败也保留以前的成功评价。学员历史和审核端均可查看历次成功评价。审核端最新自查失败时仍保留旧历史供参考。

AI 自查限额为每位学员每分钟 3 次、每小时 20 次，历史记录读取不消耗此限额。

## 页面离开与恢复

学员输入即时保存在本机，键包含任务 UUID、任务版本和任务 revision，避免不同账号任务或新一轮修改互相覆盖；可编辑状态下停止输入 1.2 秒后自动保存服务器草稿。点击自查时，服务器先保存链接再发起 AI 请求。返回或刷新时恢复草稿，并通过独立的只读 GET 路由每 3 秒读取自查状态，避免等待 Server Action 队列。恢复状态前暂停提交；RUNNING/SENDING 保持等待按钮，完成或失败后恢复操作并显示结果提示。返回页面不会自动重新发起 AI 自查。旧会话缺少草稿时可从该任务的自查记录找回链接，主动清空的本机草稿不会被历史记录重新填入。

## 验证

2026-10-20 已解决评论恢复修复：更新原 AI 回复成功后，查询该评论的 is_solved；若为 true，则 PATCH is_solved=false，并再次读取确认未解决。已是未解决状态不重复 PATCH。更新内容成功但恢复或核对失败时按 UNCERTAIN 处理，不误报完成、不自动重复写入，也不新增另一条评论。本次已使用文档应用恢复测评三原评论并读回确认 false，正文和 @ 未改变。

2026-10-20 主动重测与历史展示修复：学员每次点击开始 AI 自查时生成新的 request_id；服务器将其作为本轮 attempt_id，即使飞书正文未变化也发起新一轮评价。同一次请求的重复发送、正在运行中的重入和已成功归档请求的重放不重复调用模型或写评论。不带 request_id 的兼容调用仍保留按正文复用结果的行为。再次自查先归档上一轮成功评价，仍更新同一个标题评论；自查动作完成或失败后都读取完整服务器历史，弹窗可以同时显示错误与既有记录，不再把单条 POST 返回值伪装为全部历史。

2026-10-19 任务匹配修复：测评二、三先按当前官方题目正文提取各题独有文字，与学员正文核对；不以标题、题数或通用答题说明认定任务。题干不匹配或缺乏确认依据时停止自查，不调用模型、不写评论，也不将新文档占用到错误任务。保留题干的部分作答、空白答案或错误答案可以进入评价，答案正确性不属于匹配门槛。只有自写答案而未保留可对应题干时，会要求补齐当前任务题干。该确定性检查覆盖测评二和三；所有任务的模型输出还必须明确给出 task_match=matched，mismatched/uncertain 均不发表评论。

旧版完成结果也不能绕过测评二、三的正文检查；规则版本更新后，点击自查将重新评价并按原有机制更新同一条评论。历史已发布评价不自动删除，不能把之前放错任务产生的评价作为当前任务依据。此次真实验证只读取文档和调用模型，没有写入评论或改动学员进度。

Review 审核详情会按固定提交正文中的每个飞书答题链接显示已保存的 AI 评价。关联同时限定组织、学员、任务和文档；没有匹配记录时明确提示，不借用同任务其他文档的结果。知识库链接匹配自测记录里已保存的原始链接，docx 链接匹配解析后的文档 token。审核读取不调用外部服务、不触发新评价或评论、不改变审核状态。评价标注生成时间和自测文档版本，不声称覆盖后来改动的正文。

## 评论末尾 @ 当前文档所有者

用户已确认通知目标改为“当前文档所有者”，只通知一位已核验的真人。使用 `AI_COMMENT_MENTION_OWNER=true` 在本地启用。旧的历史修改者识别方案及其开关已移除。

使用文档应用的凭证调用 `/drive/v1/metas/batch_query?user_id_type=open_id`，只读取本次答题文档的 `owner_id`；不会使用 `latest_modify_user`、原创建者、当前学员姓名或 AI 输出猜测收件人。通过同一应用的通讯录用户接口核对 open_id 与有效 user_id，身份无法核实时明确失败，不给机器人或未知对象发通知。普通人的名字含“小助手”等字样也不会因此被排除。

AI 生成评价后，再核对所有者与文档版本是否变化。通过后将结构化 `mention_user` 元素加在原标题汇总评论末尾，只发送一条评论。所有者 ID 不会传给模型。已经完成的自查仍返回历史结果，不补发评论或通知；发送结果不确定时仍禁止自动重发。

相关应用权限：读取文档、创建评论、读取文档元数据（`drive:drive.metadata:readonly` 或已具备的 `drive:drive`），以及当前应用已有的通讯录基础信息与用户 user ID 字段权限。权限和通讯录可见范围都以实际接口结果为准。

`tests/test_ai_comment_mentions.py` 覆盖所有者与最后修改者不同、身份不匹配、应用 ID、权限失败、所有者转移、结构化 @ 及重复请求只发送一次。测试不发送真实评论。只读联调核验真实所有者，不等同于用户已收到实际通知。
