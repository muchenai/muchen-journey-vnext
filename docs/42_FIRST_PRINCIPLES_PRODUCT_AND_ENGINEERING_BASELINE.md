# 42｜第一性原理产品与工程总基线

状态：`APPROVED_FOR_BUILD`
版本：V1.0
日期：2026-08-13
Owner：Product Owner + Tech Lead + Design Owner + QA/UAT Owner
适用范围：Muchen Journey 的需求、设计、开发、测试、发布与运营

## 1. 本次重置结论

Muchen Journey 的首要产出不是模块、页面、接口、工作包、门禁或文档，而是：

> 一名真实新人无需研发人员解释，能从邀请进入，理解当前目标，完成真实学习与输出，获得主管反馈，修订或通过，并清楚知道下一步；主管和运营能用自己的真实身份完成相应工作，且业务事实安全、可追溯、可恢复。

过去一个月的主要偏差不是业务逻辑复杂，而是交付单位错误：以“模块实现、合同覆盖、候选部署、门禁数量”为完成单位，晚于真实浏览器才验证用户是否看得懂、进得去、做得完。因此出现了基础设施较完整，但入口、会话、角色、材料链接、默认展开和页面语言持续暴露小问题的结果。

本文件建立全项目最高产品基线。它不抹去 01–41 的历史事实，但在未来实现发生冲突时优先于旧工作包和旧实现说明。

## 2. 不可让步的六条产品公理

### FP-01｜真实用户结果高于系统构件

- 用户完成一个真实闭环，才产生产品进度；
- 代码、迁移、接口、页面、部署和自动化只属于实现证据；
- “机器通过”不得写成“用户可用”；“已部署”不得写成“已验收”。

### FP-02｜每个页面必须消除一个用户不确定性

页面只回答当前最重要的问题：我在哪、为什么、现在做什么、完成后会发生什么。首屏最多一个主目标和一个主动作；关键任务要求、学习材料和恢复动作默认可见，不把首次使用所需信息藏在折叠区。

### FP-03｜视觉先建立方向，文字只补足细节

- 进度、状态、可行动性和阶段关系优先由位置、层级、形状和动效表达；
- 文字不得重复标题、按钮或已经被视觉表达的信息；
- 默认页面文案以“删去后用户是否会犯错”为保留标准；
- 探索感来自目标、选择、反馈和推进，不来自游戏皮肤或口号堆叠。

### FP-04｜身份识别人，角色授予能力，会话只证明当前是谁

飞书 OAuth 的职责是确认一个外部身份对应哪个内部 `User`。`RoleAssignment` 决定该用户在组织范围内拥有哪些能力。会话绑定 `user_id + organization_id + identity_version`，不得永久固化单一角色。

因此：

- 同一个人可以同时拥有 Content Editor、Reviewer 或 Operator 等多个角色；
- 增加/撤销角色后无需重新绑定身份，刷新后的授权判断必须生效；
- `/content`、`/review`、`/ops` 每次由服务端基于有效角色授权；
- 撤销外部身份或停用用户会失效相关会话；
- 禁止为了修复访问问题直接改业务表、取消历史撤销或盲目追加角色。

### FP-05｜业务事实唯一，界面和集成都不是事实源

Journey、Enrollment、Assignment、SubmissionVersion、Evaluation、Outcome 与 RoleAssignment 是服务端权威事实。浏览器 cookie、飞书、页面状态、缓存和通知只能引用事实，不能各自产生第二状态机。

### FP-06｜复杂度必须由已验证的用户问题购买

没有真实阻塞证据，不新增通用平台、可选集成、第二部署路径、复杂 IAM、跨故障域、附件、消息或抽象。两次同类失败后先审视模型和流程；第三次之前必须有明确根因与简化方案，禁止继续叠补丁。

## 3. 产品真相与 P0 边界

### 3.1 正式探索营产品真相

P0 是单组织、私密名单、一天内可完成的新人启航探索营：

1. 邀请与安全进入；
2. Day 0 看见完整旅程；
3. 四个认知宝藏：主管维护的真实学习材料 + 学习确认/小任务；
4. 三项能力评测：真实题面、Learner 输出、独立人工评审；
5. 至少支持一次“要求修订 → 安全重新进入 → 再次提交”；
6. 三项评测均有人工结论后，产生结果、反馈和人工准入；
7. 运营可邀请、分配、处理身份与异常，不能通用改库。

### 3.2 P0 不需要证明的事情

- 企业级多组织规模、跨地域灾备或完整 GA；
- 附件、真实通知、AI 自动判断、复杂报表或通用 CMS；
- 游戏经济、排名、虚拟人物或社交系统；
- 把旧系统恢复为运行时事实源。

### 3.3 P0 上线定义

`P0_LIVE_CONTROLLED` 仅表示 Journey V3 在 `journey.muchenai.com` 面向单组织私密 cohort 可用，具备维护页/回退、备份和最小观测；不等同完整 production release gate 全部通过。

## 4. 目标角色与真正要完成的工作

| 角色 | 一次成功使用必须做到 | 不能要求其理解 |
| --- | --- | --- |
| Learner | 进入、知道当前站、打开材料、完成小任务/评测、看到反馈、继续 | UUID、版本、状态机、migration、运营术语 |
| Reviewer | 用本人身份看到授权队列、阅读固定提交、给出通过/修订结论 | 重新绑定同一身份、寻找隐藏入口、理解内部 scope ID |
| Content Editor | 用本人身份维护草稿、预览并交由 Operator 发布 | 数据库、JSON、内部 TaskVersion ID |
| Operator | 管理内容发布、角色授权、邀请与异常恢复并留下审计 | 直接 SQL、临时脚本、复制密钥 |
| QA Recorder | 记录真人路径、结果和缺陷，不代替其他角色完成 UAT | 用自动化结果推定真人感受 |

## 5. 身份与权限目标模型

### 5.1 权威关系

```text
ExternalIdentity ── identifies ──> User
User ── has many ──> RoleAssignment(scope, status, valid_from/to)
Session ── proves ──> User + Organization + identity_version
Request ── authorizes ──> active RoleAssignment + resource scope
```

### 5.2 P0 必须满足的不变量

- `provider + subject` 只映射一个有效内部用户；
- 一个用户可以有多个有效角色；
- 角色变更不复制 ExternalIdentity，不创建平行用户；
- 会话中不保存可长期漂移的唯一 role；若缓存 capabilities，必须带版本并可失效；
- 所有受保护路由在服务端重新授权；
- Reviewer、Content Editor 同人兼任时能在两个工作台之间切换；
- 角色授予/撤销、会话失效、身份撤销都有脱敏审计；
- 任何恢复动作必须使用有意图的运营命令或产品界面。

### 5.3 当前实现差距

当前实现把 OAuth、身份绑定、单角色会话和路由进入混合在多条路径中。角色虽可成功写入，Reviewer 登录仍可能因会话固化角色、回调目的或历史身份状态而失败。该问题属于身份模型缺陷，不再按单页面 OAuth bug 逐次修补。

## 6. Learner 体验合同

每一站必须按以下顺序呈现：

1. **当前站与进度**：视觉路线点与线共享坐标；状态不漂移；
2. **这站要得到什么**：一句结果导向标题；
3. **学习输入**：可点击、可访问、由内容负责人批准的材料；
4. **任务要求**：首次进入默认展开，最多 3–5 条可执行要求；
5. **唯一动作**：继续学习、提交或修订之一；
6. **完成反馈**：保存状态、等待谁、预计何时以及下一步。

禁止：空白大文本框先于输入、把 URL 当普通正文、重复“进入这一站”、隐藏任务要求、用开发术语解释状态、让错误页只显示 JSON。

## 7. 交付与验证的最小单位

一个工作包必须是可由真人感知的纵向切片，并按以下顺序退出：

1. 用一句话定义用户结果；
2. 画出首屏/关键状态，进行 5 秒理解测试；
3. 固定内容和失败/恢复路径；
4. 实现最小服务端事实和浏览器界面；
5. 自动化验证不变量、权限、三视口和错误恢复；
6. 至少一名目标角色在真实浏览器完成；
7. 记录用户是否成功、在哪里犹豫、是否需解释；
8. 只有 1–7 都通过，才记为产品完成。

## 8. 质量分层与证据语言

| 层级 | 能证明 | 不能证明 |
| --- | --- | --- |
| 单元/契约 | 规则、状态、接口结构 | 页面好用、真实身份能进入 |
| 集成/迁移 | 数据不变量和升级路径 | 用户理解、OAuth 浏览器完整链路 |
| 浏览器自动化 | 真实构建中的跳转、cookie、可见元素 | 真人是否有参与感、内容是否有意义 |
| 真人任务测试 | 理解、操作与主观体验 | 大规模容量和长期稳定性 |
| 运行观察 | 真实故障、支持成本和留存 | 未发生风险永远不存在 |

任何文档必须使用上述证据语言，不再使用一个“完成”覆盖所有层级。

## 9. 决策与停止规则

- 同类身份、路由、会话或页面理解问题出现第二次：停止局部修复，提交模型级根因；
- 同一功能两次部署后仍未完成真人主路径：停止部署，先在本地真实浏览器闭环；
- 新工作包不能说明具体用户和可观察结果：不得开工；
- 需要用户反复手动配合才能证明基础行为：将该路径列为产品缺陷；
- P0 blocker 未清零时，不开始 P1/P2 实现；
- 日期压力可以缩小范围，不能降低身份、数据完整性、恢复和真实主路径底线。
