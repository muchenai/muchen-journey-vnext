# 共享底座 01｜产品行为基线与来源优先级

## 1. 施工判断法

每个需求进入开发前依次回答：

1. 用户最终要完成什么可观察结果？
2. 该行为来自哪个正式来源或 Owner 裁决？
3. 它是否会产生正式能力、人才、准入或生产影响？
4. 需要何种证据和真人 Gate？
5. Mini 现有技术载体是复用、适配、封存还是废弃？
6. 如何证明失败时不会越权？

答不出来源、Owner 或验收证据的事项只能进入 `OWNER_CONTENT_BINDING_REQUIRED`，不得进入生产行为。

## 2. 权威层级

| 层级 | 定义 | 处理方式 |
| --- | --- | --- |
| L1 | Owner 明确裁决 | 直接转为不变量/验收合同 |
| L2 | 已验证业务方案：探索营 V1.0、新手村 V1.0 | 继承核心行为；与 L1 冲突时按 L1 |
| L3 | 获批治理升级：V0.7 | 继承证据、权限、人审、申诉、审计；不继承被裁决否定的范围 |
| L4 | 模块执行计划：AI学院等 | 转为模块内容/运营合同 |
| L5 | Mini 技术运行基线 | 复用载体；必须适配 L1-L4 |
| L6 | 候选原型、旧页面、旧数据 | 只作参考；不得自动升格为产品事实 |

## 4. 变更控制

以下变更必须重签产品合同：

- 四宝藏名称、顺序或结果包语义改变；
- 任务状态机、人工 Gate 或申诉变化；
- 真实项目任务开始持有生产凭证或直接执行生产动作；
- 积分开始影响正式能力/人才结论；
- AI开始写入 PASS、准入、淘汰、认证或成长终结论；
- 数据等级、可见范围、保留期或外部集成变化；
- 首发模块或 25 人受控范围变化；
- 候选 SHA、内容包 hash 或 migration revision 在签署后漂移。

内容修订必须经历：`DRAFT → DOMAIN_REVIEW → BOUNDARY_REVIEW → PILOT → PUBLISHED → MONITORED → REVISED/RETIRED`。发布后需要用小测、边界案例、现场抽查或反例对比验证口径一致；只发布文档不算生效。

## 5. 不采纳的反模式

- 面向 AI 的页面：首屏堆 stage、Gate、hash、状态码而不说明用户要做什么；
- 八站/多地图自动替代业务意义；
- 点击“我完成了”直接推进正式进度；
- AI或机器测试生成真人签署；
- 积分排行榜直接生成高潜、淘汰或准入；
- 先做大而全数据模型，再等内容来填；
- 为赶期限把合成脚本记为真实 UAT；
- 因旧数据不完整而冻结新产品；
- 因代码已实现而反向宣布产品已批准。
