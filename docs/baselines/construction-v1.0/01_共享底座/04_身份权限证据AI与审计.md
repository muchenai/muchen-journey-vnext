# 共享底座 04｜身份、权限、证据、AI 与审计

## 1. 角色与职责分离

| 角色 | 允许 | 禁止 |
| --- | --- | --- |
| Learner | 看自己任务/提交/反馈/结果/申诉 | 看他人私密证据、修改评审 |
| Reviewer/Mentor | 看明确分配对象、审核固定版本 | 审自己、越模块/越组织查看、代替学员提交 |
| Content Editor | 起草材料/任务/Rubric | 自行发布高影响内容或签署结果 |
| Module Operator | 发布已批版本、分配、看队列/SLA | 代替 Reviewer 作正式判断 |
| Module Owner | 批准模块使命、内容、任务、Rubric和运营 | 绕过安全/QA直接发布生产范围 |
| Data/Security | 批数据等级、可见范围、保留期、集成边界 | 替代业务判断 |
| QA/UAT | 验证产品与合同 | 生成业务内容或替业务Owner签署 |
| Release/Ops | 构建、部署、监控、回滚 | 自己充当独立发布复核人 |
| Independent QA/Release Reviewer | 复核固定候选与证据 | 参与构建后仍自称独立 |
| Admin | 身份、权限、故障和审计 | 改写人才/能力事实 |

屠元琦同时承担新手村运营、Reviewer/Panel Owner 和 QA/UAT 运营 Owner，不意味着她可以在同一案例兼任任务运营、唯一 Reviewer 与独立 UAT。冯宇汀是独立 QA/Release Reviewer，不应成为候选 Builder、模块 Owner 或 Release Executor。

## 2. 权限模型

授权必须同时满足：`organization_scope + role + object_assignment + purpose + time_window`。只具备角色名不足以访问数据。

关键负向测试：

- Learner A 不能枚举 Learner B 的 task/submission/result；
- Reviewer 只能看到明确分配任务；
- Operator 看聚合运营数据时不默认看到私密全文；
- Content Editor 不能直接 finalize Review；
- 系统管理员不能生成 HumanGate；
- 被撤销邀请、身份、Reviewer分配即时失效；
- 跨模块和跨组织 ID 置换返回拒绝且无侧信道泄露。

## 3. 证据权限与可信度

| Authority | 含义 | 可否单独形成正式结果 |
| --- | --- | --- |
| `PRACTICE` | 固定任务/提交产物 | 否，需要人审 |
| `HUMAN_EVALUATION` | 真人按Rubric判断 | 需与实操结合 |
| `HUMAN_OBSERVATION` | 真人观察事实 | 只能按批准用途使用 |
| `SYSTEM_FACT` | 登录、阅读、时点等 | 否 |
| `AI_ADVISORY` | AI建议 | 否 |
| `SELF_ATTESTATION` | 自述/草稿 | 否 |
| `INCENTIVE_LEDGER` | 积分/徽章 | 否 |

每条证据记录来源、版本、人、模块、时间、可见范围、数据等级、保留期、AI使用和修订链。

## 4. AI合同

允许：术语解释、格式提示、缺项检查、Rubric初评、敏感信息风险提示、Reviewer摘要、路线候选。

禁止：

- 直接给测试答案或替学员完成实操；
- 写 `PASS/NOT_PASSED/ADMIT/NOT_ADMIT/CERTIFIED`；
- 生成录用、淘汰、项目准入、岗位适配终判；
- 隐藏模型、Prompt、用途和时间；
- 将客户敏感数据送往未批准模型；
- 以AI文本冒充真人签署或学员原创。

AI 使用字段至少为：`used, purpose, model_version, prompt_version, output_is_advisory_only=true`。

## 5. 申诉

高影响 HumanGate 必须给出申诉入口、时限和政策引用。申诉为追加记录：

`SUBMITTED → IN_REVIEW → UPHELD / OVERTURNED / RETURNED_FOR_REVIEW`。

原签署人不能作为自己结论的独立复核人；新 Gate 必须引用原 Gate 和 Appeal，旧结论不可删除。

## 6. 数据最小化与保留

- 首发只收完成四模块所需最小字段；
- 真实任务只保存脱敏产物或结果引用，不复制生产资料；
- AI/系统日志不得写入密钥、完整凭证、客户原文或无关人员数据；
- 导出、纠正、删除请求有明确流程；
- 删除动作优先逻辑冻结/不可见，确需物理删除必须保留合规审计摘要；
- 旧新手村历史材料作为只读参考，不导入 Journey2.0 正式业务表。

## 7. 审计与监控

审计覆盖：登录、邀请、角色变化、内容发布、任务授权、Assignment、提交、评审、结果、申诉、积分、导出、删除、配置变化、发布和回滚。

首发监控至少包括：API/Web/Worker/DB健康，登录失败，邀请消费异常，待审/超时，通知 backlog/dead，错误率，数据库连接池，备份年龄和当前 release marker。告警必须有真人接收人和升级路径；Dashboard 存在不等于告警到人。
