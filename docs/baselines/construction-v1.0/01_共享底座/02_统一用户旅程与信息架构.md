# 共享底座 02｜统一用户旅程与信息架构

## 1. 设计目标

让人进入页面后先理解行动，而不是理解系统。每个页面必须让目标用户在 10 秒内回答：

- 我现在在哪；
- 今天只做什么；
- 为什么做；
- 交付什么；
- 谁审核；
- 截止什么时候；
- 卡住找谁；
- 完成后去哪。

## 2. 一级信息架构

```text
Muchen Journey
├── 今日行动
├── 探索营
├── 沐晨新手村
├── AI学院
├── 交付线公会
├── 我的提交与返工
├── 我的证据与结果包
├── 消息与求助
└── 个人与隐私设置

Operator / Reviewer（按角色显示）
├── 内容与任务发布
├── Reviewer队列
├── 运营看板与SLA
├── 授权与权限
├── 申诉/复核
└── 审计与运行状态
```

竞技场和 Career Map 在 9/1 首发不进入学员一级导航；若保留候选入口，必须不可点击并明确“后续开放”，不得制造完成预期。

## 3. 统一首页

### 首屏

1. 欢迎语和当前批次；
2. 一张唯一“现在只做这一步”的行动卡；
3. 任务名称、预计时间、截止时间、Reviewer、状态；
4. 主按钮：`开始/继续/修改后重新提交/查看结果`；
5. 次按钮：`查看要求`、`遇到问题`。

### 第二屏

- 四模块卡片：为什么进入、当前状态、下一步；
- 我的待返工、待审核、待确认；
- 不展示对用户无意义的内部 Gate ID、schema、hash。

### 第三屏

- 结果与成长：已确认事实、真人反馈、下一行动；
- 游戏积分单独显示，明确“仅作激励，不代表能力结论”。

## 4. 统一任务页

固定顺序：

1. `这一步要解决什么`；
2. `完成后你会得到什么`；
3. `输入材料`；
4. `交付物`；
5. `完成标准/Rubric`；
6. `边界与禁止事项`；
7. `Reviewer与求助路径`；
8. `开始/保存草稿/提交`；
9. `历史版本和反馈`。

真实任务额外展示：授权人、数据等级、可见范围、生产系统位置、Journey 不代执行声明、保留期。

## 5. 状态文案

| 内部状态 | 学员文案 | 主行动 |
| --- | --- | --- |
| `AVAILABLE` | 可以开始 | 开始任务 |
| `IN_PROGRESS` | 正在进行 | 继续完成 |
| `SUBMITTED` | 已提交，等待领取审核 | 查看提交 |
| `IN_REVIEW` | Reviewer 正在审核 | 查看要求/求助 |
| `NEEDS_REVISION` | 需要修改 | 查看反馈并修改 |
| `PASSED/COMPLETED` | 已通过 | 查看结果/下一步 |
| `CANCELLED` | 已取消 | 查看原因 |

不得给 `SUBMITTED` 使用“完成”，不得给 AI 初评分使用“通过”，不得给下一训练阶段建议使用“录用/淘汰/项目准入”。

## 6. Reviewer 工作台

首屏显示：今日待审、已超 SLA、待返工复审、替补队列、本人容量。单条审核必须固定展示任务版本、SubmissionVersion、RubricVersion、AI建议标签、历史反馈和冲突声明。

Reviewer只能执行服务端返回的动作：`START_REVIEW / REQUEST_REVISION / PASS`。正式结论必须逐项反馈并写总体理由；提交后不可覆盖，只能通过新评审/申诉链路追加修订。

## 7. Operator 工作台

Operator 管发布、分配、SLA、异常和通知，不代替业务 Reviewer 作判断。看板至少包含：

- 未开始、进行中、待审、返工、已通过；
- Reviewer容量、超时和替补；
- 内容/任务版本；
- 通知失败；
- 申诉待办；
- 批次和模块完成率；
- 运行健康与邀请冻结开关。

## 8. 可用性验收

- 3/3 目标学员无需讲解找到唯一下一行动；
- 3/3 能复述产物、Reviewer、边界和求助路径；
- 2/2 Reviewer 能完成一次返工与一次通过；
- 任何角色都无法从页面误解为 AI/积分/点击已产生正式结论；
- 手机 390px 与桌面 1280px 均无横向溢出，关键 CTA 在首屏可见；
- 错误态给出恢复动作，不只显示状态码。
