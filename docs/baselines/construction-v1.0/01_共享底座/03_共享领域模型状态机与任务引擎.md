# 共享底座 03｜共享领域模型、状态机与任务引擎

## 1. 设计原则

四模块共享一个任务/提交/审核/证据内核，差异放在版本化模块配置与任务包中。禁止四个模块各建一套身份、任务、积分、证据或通知系统。

## 2. 核心对象

| 对象 | 权威职责 | 关键约束 |
| --- | --- | --- |
| `Person/User` | 组织内唯一自然人引用 | 跨模块只引用，不复制人员事实 |
| `RoleAssignment` | 角色与组织 scope | 最小权限、可撤销 |
| `ModuleDefinition/Version` | 四模块配置与发布版本 | 发布后不可变；新版本替代 |
| `ContentItem/Version` | 学习材料、示例、规则 | 来源、Owner、版本、敏感度、有效期 |
| `TaskDefinition/Version` | 稳定任务身份与不可变版本 | 目标、非目标、输入、产物、Rubric、Reviewer、边界 |
| `ControlledTaskAuthorization` | 真实任务授权事实 | 缺任一安全字段不得发布 |
| `Enrollment/Membership` | 人进入模块/批次的关系 | 不等于能力或资格结论 |
| `Assignment` | 人与固定 TaskVersion 的执行关系 | 不得静默换版本 |
| `Submission/SubmissionVersion` | 提交容器和追加版本 | 旧版本不可覆盖 |
| `Review/Evaluation` | Reviewer领取与正式判断 | 绑定固定提交和Rubric；必须写理由 |
| `Evidence` | 来源化、可见、可修订的事实 | AI、自述、积分不能冒充真人评估 |
| `HumanGate` | 真人签署的正式判断 | 固定证据集合、理由、签署人、申诉策略 |
| `ResultPackage` | 面向使用者的完成事实与下一行动 | 区分事实、真人判断、AI建议和积分 |
| `Appeal` | 对 Gate 的追加复核 | 原结论不被覆盖；复核人独立 |
| `IncentiveLedger` | XP/积分/徽章事实 | 单独账本，只引用贡献事件 |
| `AuditEntry` | 谁在何时以何理由做了什么 | 安全裁剪、不可静默修改 |
| `Outbox/Notification` | 跨进程可靠通知 | 失败不回滚正式业务事实 |

## 3. 正式任务状态机

```text
DRAFT
  └─ publish(内容/安全/Reviewer齐全) → AVAILABLE
AVAILABLE
  └─ start(learner) → IN_PROGRESS
IN_PROGRESS
  └─ submit(fixed task version) → SUBMITTED
SUBMITTED
  └─ reviewer_start → IN_REVIEW
IN_REVIEW
  ├─ request_revision(reason) → NEEDS_REVISION
  └─ pass(reason,rubric) → PASSED
NEEDS_REVISION
  └─ resubmit(new SubmissionVersion) → SUBMITTED

任意未终结态 ─ cancel(reason,authorized actor) → CANCELLED
```

现有数据库 `AssignmentStatus.COMPLETED` 可暂时承载产品 `PASSED`，但 API/UI/审计必须统一对外语义并保留人工 Evaluation 来源；不得在同一产品中混用两个含义。

### 禁止转换

- `AVAILABLE/IN_PROGRESS → PASSED`；
- `SUBMITTED → PASSED`（缺 `IN_REVIEW` 和 Evaluation）；
- `AI_ADVISORY/SELF_ATTESTATION/INCENTIVE_LEDGER → PASSED`；
- 覆盖旧 SubmissionVersion 或 Evaluation；
- 任务发布后原地修改 TaskVersion。

## 4. 学习与能力分离

```text
LearningMaterialCompletion = 看过/完成某材料的系统事实
PracticeEvidence = 固定任务、提交版本与产物事实
HumanEvaluationEvidence = 真人按 Rubric 的判断
FormalResult = PracticeEvidence + HumanEvaluationEvidence + HumanGate(PASS)
```

学习完成率可用于提醒，但不能构成能力结果。

## 5. 真实任务授权

`ControlledTaskAuthorization` 至少包含：

- taskVersionId、项目/业务来源、授权人、授权理由；
- 环境：`SIMULATION / CONTROLLED_REAL_TASK`；
- 数据等级、脱敏方式、允许输入和禁止输入；
- 参与人/可见范围；
- 指定 Reviewer、替补、SLA；
- Journey 外生产系统和授权执行人；
- 结果证据最小字段；
- 保留期、删除/封存规则；
- 生效/到期时间、撤销状态。

服务端必须验证：`CONTROLLED_REAL_TASK` 不携带生产写凭证；任何“提交通过后自动写业务系统”的 hook 首发一律禁止。

## 6. 双账本

能力证据账本和游戏激励账本只通过来源事件单向关联：

```text
Evaluation(PASS) → ContributionFact → IncentiveLedgerEntry
```

反向禁止：

```text
points/xp/rank/badge -X-> Evidence / HumanGate / ResultPackage formal conclusion
```

积分更正以追加正负分录完成，不覆盖历史；兑换消耗可用余额，但不改变累计贡献记录。

## 7. 幂等、并发与审计

- 所有 mutation 带 `idempotency_key` 与 `expected_revision`；
- Reviewer finalize、提交和分配采用数据库约束保证一次性；
- Outcome/ResultPackage 与 Outbox 在同一事务产生；
- 通知失败只能进入重试/死信，不能回滚已经签署的结果；
- 每次状态变化记录 actor、reason、source version、before/after、occurred_at；
- 任何管理员修复通过受控命令追加事实，禁止直接后台改状态。

## 8. 首发数据库策略

- 以 `Muchen Journey2.0` 当前 Alembic 链为空库重建基础；
- 新共享对象优先适配现有表和共享 domain contract；确需新表必须有 migration、downgrade/forward fix 与回滚影响说明；
- 旧新手村 23 表不做正式迁移，`migrate_record_count=0`；
- Journey2.0 开发/测试数据可在备份并确认环境后重置；生产或历史源不可清空；
- 所有 UAT 使用候选环境和受控测试/试点账户，不借用历史数据伪造业务结果。
