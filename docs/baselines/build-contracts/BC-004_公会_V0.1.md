## 1. 贡献契约

使用者是公会成员、导师/Reviewer、项目Owner和人才发展Owner。公会使成员围绕一种明确能力进行短周期共同实践，留下可复核产出、导师反馈和下一次实践建议；它不是聊天群、内容目录、排行榜或按岗位名称自动分人。

## 2. 平台与插件边界

共享平台负责身份、权限、任务、提交、审核、证据、通知、积分、申诉、审计和发布。每个公会插件只定义：公会使命、目标能力、适用人群、加入条件、任务包、Rubric、导师池、活动节奏、证据有效期和退出/转会规则。

禁止每个公会重新实现账户、积分、证据或通知系统。

## 3. 第一发布最小闭环

第一发布至少选定一个真实公会，完成：

1. 成员查看公会使命、能力模型、导师和加入条件。
2. 真人确认加入或试炼资格；不得只按积分自动加入。
3. 成员领取一个短周期任务，可为模拟任务或通过安全Gate的受控真实任务。
4. 成员提交产出；导师按Rubric审核并要求返工或通过。
5. 通过后写入公会实践证据和导师反馈；积分另账记录。
6. 成员得到下一任务、继续练习、转公会或暂缓的人工建议。

Journey不直接执行生产作业；任何真实项目任务都必须继承BC-002安全边界。

## 4. 真实状态与治理

公会成员状态与任务状态分离。成员可为 `APPLIED / ACTIVE / PAUSED / EXITED`；任务仍走统一提交—审核—返工/通过链路。加入、退出、认证和人才结论不得由排行榜或AI自动决定。

AI只做任务匹配建议、自查、初评和导师摘要。成员必须能看见建议依据并选择不采纳。

## 5. 候选处置

当前“交付线工会”原型只作为一个候选插件，不自动成为首批正式公会。其合成沙盒、角色责任说明和待复核草稿交互可参考；“本地草稿形成”不能替代正式提交和导师审核。

## 6. 验收 Gate

| Gate | 通过标准 | Owner |
| --- | --- | --- |
| P-01 公会名单 | 第一发布公会名称、使命、目标能力和Owner由业务批准 | 产品 Owner＋公会 Owner |
| P-02 插件包 | 每个公会均有任务包、Rubric、导师池、版本和证据规则 | 公会 Owner |
| M-01 共享复用 | 公会不复制身份、任务、积分、证据和通知核心 | Tech Lead |
| H-01 成员可用 | 3/3目标成员能说明公会目标、任务边界、导师和下一行动 | 公会 Owner |
| H-02 导师可用 | 导师能在SLA内完成一次返工和一次通过 | 导师 Owner |
| S-01 真实任务 | 受控真实任务通过BC-002安全演练 | 项目Owner＋Data/Security |
