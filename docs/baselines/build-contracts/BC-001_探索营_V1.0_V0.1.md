# BC-001｜探索营 V1.0 Build Contract V0.1

> 状态：`BUILD_STARTED_BY_DECIDER_OVERRIDE / TEAM_ACCEPTANCE_AND_CONTENT_PENDING / NO_RELEASE`  
> 开发授权：见 `../Muchen_Journey_全模块开发解锁决议_V0.1.md`；未签署项继续作为发布前Gate。
> MAP-ID：MAP-002、007、015—018、021—023  
> 权威方向：探索营V1.0四宝藏；个人成长基线作为结果包；Day 1只决定下一训练阶段。

## 1. 贡献契约

使用者是首次进入Muchen Journey的学员、探索营Reviewer和下一训练阶段Owner。完成后：

- 学员能说明四个宝藏分别解决什么问题，并完成三项与真实工作方式相似的实操；
- Reviewer能基于固定版本提交和Rubric给出可解释、可返工的人工结论；
- 下一训练阶段Owner能读取个人成长基线结果包，安排继续、补强复测或暂缓；
- 任何人都不能把本结果直接解释为录用、淘汰或真实项目准入终判。

不以页面访问、材料点击、积分、AI分数或“完成八站”作为贡献完成证据。

## 2. 范围

包含：受控邀请与身份确认、Day 0材料和问题、四个宝藏、三项核心实操、提交/返工、人工结论、个人成长基线结果包、下一训练安排、申诉入口。

不包含：项目规则正式训练、生产作业、录用/淘汰终判、积分排名分流、第五宝藏、BOSS副本。

技术上可以存在 `Day 0＋四宝藏＋三评测` 八个stage，但用户产品结构必须呈现为“四宝藏认知＋三项能力实操”，不得再用“八站自助闯关”替代业务意义。

## 3. 黄金路径

入口：有效邀请，身份确认，绑定一个已发布的探索营JourneyVersion。

1. 学员看见今天要解决的问题、人工评审边界和求助方式。
2. 异步完成Day 0和四宝藏学习输入；每项保留来源与版本。
3. 为每项核心实操创建正式Assignment，展示目标、输入、约束、交付物、时限、Rubric、Reviewer和求助路径。
4. 学员提交产物；系统只标记 `SUBMITTED`。
5. Reviewer领取并人工审核，选择 `NEEDS_REVISION` 或 `PASS`，必须写理由。
6. 返工时保留旧版本，学员只修订有问题部分并重新提交。
7. 三项实操均有有效人工结论后，Operator生成个人成长基线结果包。
8. 授权真人签署“进入下一训练阶段 / 补强后复测 / 暂缓”，并告知申诉入口。

## 4. 正式状态与数据

学习完成记录与能力证据分开。`LearningMaterialCompletion`只证明材料行为；`SubmissionVersion＋Evaluation`才构成能力证据。个人成长基线结果包至少含：完成事实、三项证据摘要、Reviewer结论、优势、待发展项、下一行动、签署人、时间和申诉状态。

现有 `JourneyAdmissionDecision` 可以暂作技术载体，但产品/API/UI不得呈现招聘式 `ADMIT / NOT_ADMIT` 语义；开发前必须通过兼容设计映射为“下一训练阶段决定”，并证明不会改变人事事实。

## 5. AI与真人边界

AI可以做提交前自查、Rubric初评、缺项提示和Reviewer摘要。AI输出必须标记建议、来源版本和生成时间。AI不得写入 `PASS`、下一训练阶段终结论或个人成长基线签署字段。

## 6. 复用与重写

复用：Invite、IdentitySession、Enrollment、Journey/Task版本、Assignment、LearningMaterialCompletion、SubmissionVersion、Attachment、Review、Evaluation、Outcome、Handoff、Audit和现有三角色入口。

重写：当前八站叙事、自证完成、V2/V3自动准入措辞、把个人成长基线当第五宝藏的内容、只给AI看的后台元数据式页面。
